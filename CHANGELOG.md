# История изменений

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.0.0/),
версии — по [семантическому версионированию](https://semver.org/lang/ru/).

## [Не выпущено]

### Добавлено — общий HTTP-режим: один коннектор на много пользователей

- `1c-odata-mcp-http` (`npm run start:http`, `dist/http.js`) — Streamable HTTP без сессий: учётка базы приходит с каждым запросом в заголовке `X-OneC-Connection`, доступ к самому коннектору — по общему ключу `Authorization: Bearer`; подключения — в пуле. Подробно — [docs/HTTP-MODE.md](docs/HTTP-MODE.md).
- Запись — только инструменты из белого списка `ODATA_HTTP_WRITE_TOOLS` (пусто — ни одного); `write.operation.status` — вместе с ними, для сверки после сбоя. Шлюз `meta.*` в общем режиме не публикуется: инструменты для модели отбирает клиент.
- Печатные формы `read.document.print_*`, вложения `read.files.*` и PDF при создании (`quick_invoice`, `quick_sale`, `quick_reconciliation`) отдаются ресурсом MCP; на диск коннектора ничего не пишется (`printToDisk=false`), файлы больше 10 МБ не отдаются.
- `read.system.health_check` в общем режиме не показывает путь журнала записи на сервере.

### Добавлено — для форм записи в чате

- Предпросмотр пишущих инструментов несёт `view`: подписи полей, названия вместо GUID, строки табличных частей, итоги. Ответ создания — номер, дата, сумма и проведён ли документ.
- `read.catalog.list_catalog`: отбор по владельцу `owner` (договоры контрагента, банковские счета организации, контактные лица объекта) и планы счетов (`ChartOfAccounts_*`, например налоговый).
- `read.document.search_documents`: поиск по номеру — `number` (точно, с префиксами и ведущими нулями) и `query` (подстрока).
- `read.schema.describe_entity`: цели навигаций (`navigations` — `{name, toType, collection}`), чтобы клиент знал, из какого справочника подбирать ссылку.

### Изменено — база Казахстана

- Разрешены ещё 6 инструментов записи, проверенных на фейковой базе РК (пишут только свои реквизиты, без российских счетов и НДС): `write.counterparty.update_counterparty`, `write.catalog.update_nomenclature`, `write.counterparty.create_contact_person`, `write.document.copy_document`, `write.entity.create_folder`, `write.entity.move_to_folder`. `write.document.add_document_line` и `remove_document_line` остаются вне списка: они пересобирают строки с российской ставкой НДС и счетами.
- `write.counterparty.update_counterparty` на базе РК: `inn` пишется в `ИдентификационныйКодЛичности` (проверка «12 цифр»), новый `kbe` — в `КБЕ`; `kpp` и `ogrn` — понятный отказ, как у создания.

### Тесты

- Фейковая 1С: метаданные из файла дискового кеша (`metadataFile`), не-казахстанская база БП РФ (`ruStore()`), виды субконто в формате 1С (`ValueType.Types`).
- Контрактные фикстуры предпросмотра и записи на фейковой 1С (`RECORD_FIXTURES=1`) — для пишущих инструментов РК и 18 инструментов российского профиля.

## [0.7.11] — 2026-10-21

### Добавлено — черновик извещения об отнесении в зачёт НДС (Казахстан)

- `write.vat.create_offset_notice_draft` — НЕпроведённый черновик извещения об отнесении в зачёт НДС за квартал (`quarter` «2026/2») по организации, при желании только по поставщику (`counterpartyRef`) и/или списку ЭСФ (`esfRefs`). Заполнение сверено с проведённым извещением, сформированным в 1С (только чтение рабочей базы):
  - строки (`СтрокиИзвещения`) — входящие ЭСФ, которые 1С ждёт в извещении (та же сверка, что в `read.vat.find_unoffset_esf`, группа `unoffset`); суммы — остаток регистра «Обязательства по извещениям ИС ЭСФ» по ЭСФ, рег. номер и тип ЭСФ, валюта — из ЭСФ, дата отнесения — последний день квартала, квартал «ГГГГ/К»;
  - детализация (`ДетализацияДанныхИзвещения`) — документы поступления по ЭСФ (регистр «Актуальные ЭСФ по первичным документам») с остатком регистра «Обязательства по зачёту ИС ЭСФ» за квартал (строки прихода по ставкам складываются);
  - шапка — организация, плательщик (БИН, полное наименование), тип события «Пользователь», итоги = сумма строк; номер — следующий среди извещений за год (или `number`; занятый — отказ).
- ЭСФ, уже включённые в непроведённое извещение, в черновик не попадают (дубль не создаётся); ЭСФ из `esfRefs`, которые не «не отнесены», — в `preview.skipped` с причиной. Строка без детализации и расхождение детализации с остатком по ЭСФ — предупреждения.
- Поля обмена с ИС ЭСФ (Идентификатор, РегистрационныйНомер, НомерИзвещения, Статус, Состояние, ЭЦП, ТипПодписи, автор и дата поступления в ИС, ошибки) не заполняются никогда. Документ не проводится: проведение спишет остатки регистров обязательств в учёте 1С, а принято ли извещение ИС ЭСФ, через OData не узнать — подпись, отправка и проведение остаются в 1С.
- Предпросмотр по умолчанию (шапка, строки, детализация с номерами поступлений, итоги, пропущенные ЭСФ, сводка сверки); создание — `confirm=true` с `operationId` после согласия бухгалтера.
- `read.vat.find_unoffset_esf` и новый инструмент используют общий подбор `reconcileIncomingEsf` — ответ сверки не изменился.

## [0.7.10] — 2026-10-21

### Добавлено — извещения об отнесении в зачёт НДС (Казахстан, только чтение)

Документ «Извещение об отнесении в зачёт НДС» — обмен с ИС ЭСФ; формирование, подпись ЭЦП и отправка остаются в 1С. Проводок по счетам документ не делает: проведённое извещение списывает (расход) остатки регистров накопления «Обязательства по извещениям ИС ЭСФ» (по ЭСФ) и «Обязательства по зачёту ИС ЭСФ» (по документу поступления и налоговому периоду); приход в них делают входящий ЭСФ и поступление.

- `read.vat.list_offset_notices` — список за период по организации: номер, дата, номер извещения, регистрационный номер ИС ЭСФ, статус и состояние, тип события и подписи, проведён ли, пометка удаления, итоги (оборот, НДС в зачёт, оборот без НДС / не в зачёт, НДС не в зачёт), число строк и ошибок, кварталы отнесения; общий итог и число непроведённых. Помеченные на удаление — только с `includeDeleted`.
- `read.vat.get_offset_notice` — одно извещение по `ref` или номеру (`year`, если номер повторяется): шапка, строки по ЭСФ с найденным ЭСФ (номер, дата, дата оборота, статус, вид, контрагент), детализация с первичным документом (тип, номер, дата, проведён), ошибки, сверка итогов шапки со строками и детализацией, движения проведённого извещения по регистрам обязательств.
- `read.vat.find_unoffset_esf` — входящие ЭСФ за квартал (`quarter` «2026/1») или период по дате оборота, которых нет ни в одном извещении: сопоставление по ЭСФ_Key и регистрационному номеру; помеченные на удаление ЭСФ и извещения не учитываются; отозванные, аннулированные, отклонённые ЭСФ и исходные ЭСФ, заменённые исправленным, — в группе `excluded`. Остаток регистра обязательств по извещениям показывает, что 1С ждёт ЭСФ в извещении, и даёт сумму НДС; ЭСФ без извещения и без остатка — `noObligation` (обычно без НДС), только в непроведённом извещении — `inUnpostedNotice`.
- Нет документа в конфигурации или в составе OData — понятный ответ «в этой версии 1С документа нет» и как его опубликовать.

## [0.7.9] — 2026-10-20

### Добавлено — зарплата за месяц: проверка, остатки фондов, ведомость, перечисления (Казахстан)

Суммы считает 1С: «Заполнить», «Рассчитать» и проведение расчётных документов бухгалтер делает в форме 1С. MCP суммы не рассчитывает — берёт их из остатков регистров 1С или из строк проведённого документа.

- `read.payroll.check_month` — проверка месяца по организации: документы месяца и их проведение; дубли за период (одинаковый сотрудник и вид расчёта / вид операции и работник); проведённые с пустыми суммами; ЕП и классические удержания/СН-СО в одном месяце; работающие сотрудники без начисления; доход из начисления ↔ облагаемая база в расчёте ЕП; суммы строк ↔ движения регистров (`movements`, по умолчанию да); переплата; остаток к выплате и к перечислению. Только чтение.
- `read.payroll.get_fund_debts` — остатки к перечислению по ОПВ, ВОСМС, СО, ООСМС, ОПВР, ОППВ, ЕП, ИПН (виртуальная таблица остатков регистров 1С): итог, по месяцам и по работникам; пени/штрафы — отдельно, в итог не входят. Фильтры `period`, `fund`, `asOf`.
- `write.payroll.create_payroll_statement` — ведомость «Зарплата к выплате» за месяц: строки и суммы — остаток к выплате в 1С (только положительный); касса или банк; `responsibleRef` проверяется по справочнику пользователей. Нечего выплачивать — отказ; ведомость за месяц по тем же работникам уже есть — отказ (`allowDuplicate`). Предпросмотр → `confirm=true` с `operationId`.
- `write.payroll.create_fund_transfer` (`fund`: `opv` | `so` | `ep`, `kind` — ОПВ/ОПВР/ОППВ, СО/ВОСМС/ООСМС) — перечисление в фонды: строки — остаток к перечислению за месяц или строки проведённого расчёта (`basisRef`). Получатель по умолчанию — из последнего проведённого перечисления. Повтор за месяц — отказ (`allowDuplicate`). Долг перед фондом гасит платёжное поручение исходящее (`write.document.create_document`), а не само перечисление — об этом в описании и в заметках.
- Новые записи — в списке разрешённых для казахстанской базы; `read.system.kz_document_guide` — блок «зарплата» (порядок месяца), подсказки у ведомости и перечислений.

### Исправлено

- Счета учёта номенклатуры (подстановка счетов в строках документов) в казахстанской конфигурации запрашивали российские поля регистра (`СчетУчета_Key`, `ВидНоменклатуры_Key` …), которых в нём нет. Теперь поля выбираются по метаданным: в KZ — счета БУ (`СчетУчетаБУ_Key`, `СчетУчетаНДСПоПриобретению_Key`, `СчетДоходовОтРеализацииБУ_Key`, `СчетСебестоимостиПриРеализацииБУ_Key`), без вида номенклатуры. Поведение в российской конфигурации не изменилось.

## [0.7.8] — 2026-10-20

### Исправлено — зарплатные документы, комплектация, доверенность (по проверке на Aru Market)

- `write.document.post_document` отказывается проводить зарплатные расчётные документы (начисление, расчёт удержаний, СН/СО, единый платёж, отражение в учёте, зарплата к выплате, перечисления ОПВ/СО/ЕП в фонды), если суммы пустые или нулевые: «суммы ставит 1С в форме — нажмите «Заполнить»/«Рассчитать»». Через OData 1С суммы не досчитывает, пустой документ проводился с нулями и без движений. В предпросмотре — то же предупреждение. Отмена проведения не проверяется.
- `write.document.create_document` / `update_document` для этих документов только предупреждают о пустых или нулевых суммах (в т. ч. о нулевых строках); запись не блокируется.
- `read.system.kz_document_guide`: у всех зарплатных документов подсказка «суммы считает 1С в форме».
- `write.document.post_document`: если 1С не провела документ (в т. ч. ответила страницей 1С:Фреш «сервис частично недоступен»), сообщение — «1С отклонила проведение; причина видна при проведении в форме 1С», без HTML в тексте; сырой ответ 1С — отдельным полем `rawResponse` (статус, тип, текст страницы, тело до 4000 символов).
- `write.warehouse.create_kitting` подставляет, как форма 1С, незаданные счета учёта БУ/НУ комплекта и строк из регистра «Счета учёта номенклатуры» (номенклатура → её группы → «для всех», запись организации точнее общей) и `ВидУчетаНУ` = «НУ» (через OData 1С ставила «не отражается в НУ»). Заданные явно и взятые из `sampleRef` значения не меняются. `update_kitting` дополняет счета только передаваемых строк, `ВидУчетаНУ` не трогает. Предупреждения о незаданном счёте — после подстановки.
- `write.document.create_power_of_attorney` / `update_power_of_attorney`: у ТМЦ строкой ставится единица по классификатору — `unit` (обозначение или код: «кг», «796»), по умолчанию «шт» (796); не найдена — предупреждение. Строки с номенклатурой — по-прежнему базовая единица карточки.

## [0.7.7] — 2026-10-20

### Исправлено — ЭСФ: номер, адреса и реквизиты, как в форме 1С

- `write.esf.create_draft` ставит «Номер учётной системы» (`Number`): следующий после максимального среди исходящих ЭСФ той же организации за год, в том же формате (префикс, длина; если ЭСФ ещё нет — как у счетов-фактур выданных, иначе 11 цифр). Входящие ЭСФ (номер поставщика) в нумерацию не входят. Можно задать `number`; дубль среди исходящих ЭСФ организации за год — отказ. Регистрационный номер ИС ЭСФ не заполняется.
- Адреса сторон — из регистра контактной информации: поставщик — юридический → фактический → почтовый адрес организации (у ИП — ещё адрес физлица), получатель — юридический → фактический адрес контрагента. Код страны получателя; у поставщика-резидента код страны не заполняется.
- Грузоотправитель и грузополучатель (БИН, наименование, адрес отправки/доставки, код страны грузополучателя) заполняются и для услуг, как в ЭСФ, созданных в 1С. Условия поставки и способ отправления по классификатору — из СФ; пункт назначения СФ не переносится.
- `ТипПодписи` «ЮридическоеЛицо», `СпособРасчета` «Безналичный»; `КурсВалюты` = 1 для ЭСФ в тенге (раньше брался курс взаиморасчётов валютного договора); `СпособРасчета` больше не берётся из условий оплаты.
- Предупреждения: адреса нет в контактной информации, регистр недоступен, адрес короче 3 или длиннее 400 символов.

### Добавлено — `write.esf.update_draft`

- Правка черновика исходящего ЭСФ до отправки: номер (`number` / `assignNumber`), перезаполнение сторон и реквизитов из карточек и СФ (`refreshParties`), ручные поля поставщика/получателя, адреса отправки/доставки, реквизиты шапки из белого списка, строки с пересчётом НДС и итогов. Dry-run «было → станет»; `confirm=true` — только с `operationId` предпросмотра (журнал записи); `READ_ONLY`/`writable`; входит в `KZ_WRITE_TOOLS`.
- Отказ, если ЭСФ входящий, имеет регистрационный номер или идентификатор ИС, статус не «Черновик», состояние не «Сформирован», есть в очереди отправки, истории обмена или актуальных ЭСФ; проведённый — только с `repost: true`.
- `read.system.kz_document_guide` — раздел `esf`: сценарий, нумерация, поля сторон и их источники, правила правки (непроверенные пункты помечены «проверить»).

## [0.7.6] — 2026-10-20

### Добавлено — доверенность и комплектация номенклатуры (запись, Казахстан)

- `write.document.create_power_of_attorney` / `write.document.update_power_of_attorney` — документ «Доверенность»: физлицо (`personRef`), срок действия (`validUntil`, не раньше даты документа), поставщик, договор, «на получение от», «по документу», основание и строки ТМЦ (`nomenclatureRef` — ссылка на номенклатуру с `НаименованиеТовара_Type = StandardODATA.Catalog_Номенклатура`, или `name` строкой — `Edm.String`). Доверенность не проводится; печать — прежний `read.document.print_power_of_attorney`.
- `write.warehouse.create_kitting` / `write.warehouse.update_kitting` — «Комплектация номенклатуры»: `operation` Комплектация / Разукомплектация, склад, комплект, количество, единица и коэффициент, счета учёта БУ/НУ по коду или `Ref_Key`, строки «Комплектующие» с долей стоимости; `sampleRef` — счета и настройки из проведённого документа. Предупреждения: разукомплектация без долей стоимости, комплектующие без счёта; комплект в собственных строках — отказ.
- Все четыре — в `KZ_WRITE_TOOLS`; как у остальных записей: предпросмотр по умолчанию, `confirm=true` только с `operationId` из предпросмотра (журнал записи), `READ_ONLY` / `writable` базы. Изменение проведённого или помеченного на удаление документа — отказ. Видны через `meta.list_tools` / `meta.call_tool`.
- Общая подготовка изменения документа вынесена в `prepareDocumentPatch` (`write-documents.ts`): `write.document.update_document` работает как прежде.
- Единица измерения (доверенность — `ЕдиницаПоКлассификатору_Key`, комплектация — `ЕдиницаИзмерения_Key` шапки и строк) — справочник `Catalog_КлассификаторЕдиницИзмерения` (в казахстанской базе `Catalog_ЕдиницыИзмерения` нет). Без `unitRef` подставляется базовая единица из карточки номенклатуры (`БазоваяЕдиницаИзмерения_Key`, как в форме 1С); не нашлась — предупреждение в `notes`. Найдено живым предпросмотром на тестовой базе: доверенность, созданная в 1С, хранит единицу, а предпросмотр оставлял её пустой.
- Проведение комплектации через `write.document.post_document` требует документа в реестре флоу (`KZ_FLOW`) — он добавляется отдельным изменением реестра.

## [0.6.0] — 2026-10-03

Учётная аналитика: ОСВ по счёту, проводки документа и хронология документа для аудита. Идея и первая
реализация всех трёх инструментов — **[@AlexMarinenko](https://github.com/AlexMarinenko)** ([#31]);
мы проверили их на живых базах и доработали (чистое сальдо, проводки после проведения). Плюс защита
от повтора для строк документа, назначенный `Ref_Key` и договор по умолчанию.

### Добавлено

- **`read.accounting.get_account_turnover` — ОСВ по счёту.** Сальдо на начало,
  обороты и сальдо на конец (Дт/Кт) по произвольному счёту или префиксу (`51`, `60`,
  `62`, `90.01`) за период, итогом и по субсчетам. Источник — виртуальная таблица
  `BalanceAndTurnovers` регистра бухгалтерии Хозрасчетный; счёт и организация
  фильтруются на стороне 1С. Суммы — в копейках; при превышении
  `ODATA_ANALYTICS_MAX_ROWS` — явная ошибка вместо неполной ведомости.
- **`read.accounting.get_document_postings` — проводки документа.** Все записи
  регистра бухгалтерии Хозрасчетный, сформированные одним документом-регистратором
  (любой `Document_*`): Дт/Кт (код, наименование, Ref_Key счёта, субконто),
  сумма, количество/валютная сумма, итоги Дт/Кт и свод по корреспонденциям.
  Пример: `{"documentEntity": "Document_РегламентнаяОперация", "documentRef": "919a75d1-…"}`.
  Только GET; отбор по регистратору — на стороне 1С; поля записей сверяются с
  `$metadata`; несуществующий документ, незнакомая структура записей и превышение
  `ODATA_ANALYTICS_MAX_ROWS` — явные ошибки. Счета резолвятся пакетно, суммы — в копейках.
- **`read.audit.get_document_history` — хронология документа (аудит).** Только то,
  что доказуемо по стандартному OData, раздельно: `documentDate` (Document.Date —
  учётная дата) и `refCreatedAt` — метка генерации `Ref_Key`, выведенная из UUIDv1
  (`confidence: "derived"`, UTC, ISO-8601; не проверенное время создания/выполнения/
  проведения). Для UUID другой версии/варианта метка не возвращается. `executedAt` и
  `modifiedAt` недоступны и не возвращаются. Плюс: ответственный (реквизит документа,
  имя из `Catalog_Пользователи`; сбой поиска имени — статус, а не ошибка), `DataVersion`
  как есть, наличие движений в Хозрасчетном (один GET с `$top=1` по регистратору;
  `unsupported`/`error` отличимы от «движений нет»), `evidence` и `limitations`.
  Исследование источников — [docs/AUDIT-HISTORY.md](docs/AUDIT-HISTORY.md).
- **ОСВ поясняет «красное» сальдо.** `get_account_turnover` отдаёт чистое сальдо `openingNet` /
  `closingNet` (Дт − Кт), а если в колонке Дт или Кт отрицательное значение (развёрнутое сальдо по
  аналитике), объясняет это в `note` — на счёте 62 базы ООО так и было.
- **`post_document` показывает проводки.** После проведения в ответе — число проводок, итоги Дт/Кт и
  свод по корреспонденциям (`get_document_postings`); сбой чтения проводок проведение не отменяет.
- **Защита от повтора для добавления и удаления строк документа.** `add_document_line` и
  `remove_document_line` перечитывают документ, поэтому слепой повтор после таймаута добавлял ещё
  одну строку или удалял соседнюю. Теперь они, как и создание, требуют `operationId` из
  предпросмотра и идут через журнал; `write.operation.status` сверяет их по числу строк документа
  (`found_reconciled` / `not_applied`). Повтор уже подтверждённой операции отвечается из журнала
  до повторного чтения 1С. Проверено на живой базе, включая потерянный ответ.

- **Назначенный `Ref_Key` при создании.** Проверено на живой базе: 1С принимает ссылку от клиента,
  а повтор с той же ссылкой отвергает («нарушено условие уникальности»). Теперь MCP назначает
  `Ref_Key` (UUIDv1, как у ссылок самой 1С — время создания из неё по-прежнему выводимо) при
  предпросмотре и отправляет его при подтверждении. Дубль невозможен на уровне базы, а
  `write.operation.status` сверяет создание простым GET по ссылке — теперь и для справочников
  без «Комментария» (раньше — вручную).

- **`npm run manifest`** пересобирает инструменты в `manifest.json` из живого сервера и
  синхронизирует версию; **тест согласованности** сверяет манифест, версию, раздел CHANGELOG и
  число инструментов в README / `package.json` с кодом — расхождения ловятся до релиза.

- **`health_check` показывает журнал операций** (когда запись включена): доступен ли каталог для
  записи и сколько операций ждут сверки (исход неизвестен), с их id — чтобы они не терялись.

### Изменено

- **Метка `[op:…]` в «Комментарии» выключена по умолчанию** (`ODATA_WRITE_OPERATION_MARKER=true`
  включает): сверка теперь по `Ref_Key`, а видимая бухгалтеру метка больше не нужна. Операции из
  0.5.0, созданные с меткой, `write.operation.status` по-прежнему находит по ней.

### Исправлено

- **Сверка операций 0.5.0 по метке падала для справочников** (контрагент, номенклатура, договор…):
  `write.operation.status` запрашивал поле `Number`, которое есть только у документов, и 1С отвечала
  400. Теперь у справочников берётся `Code`. Найдено живым прогоном: операция создана опубликованной
  0.5.0, ответ «потерян», сверка новой сборкой — `found_reconciled`.
- **Реализации, созданные без договора, не проводились** — 1С (БП 3.0) падала невнятной ошибкой
  модуля прослеживаемости «Преобразование значения к типу Булево» (`create_act`, `create_shipment`
  и другие документы с контрагентом). Причина — пустой договор. Теперь, как форма 1С при выборе
  контрагента, MCP подставляет договор, если у контрагента он ровно один нужного вида с этой
  организацией (покупательские документы — «с покупателем», закупочные — «с поставщиком»);
  несколько или ни одного — не угадывает, а предупреждает в предпросмотре. `post_document` до вызова
  1С понятно сообщает, что договор не заполнен, и подсказывает, как его указать. Проверено на живой базе.
- **Неверные виды операций в описаниях денежных документов:** ПКО — `ОплатаПокупателя` (не
  `ПоступлениеОплатыОтПокупателя`), списание с р/с — `ПеречислениеЗП`. Если 1С отвергает значение
  перечисления, к ошибке теперь приложен список допустимых значений из `$metadata`.

- Журнал операций создаётся при первой записи: `ODataClient` больше не требует `writeJournalDir`
  для чтения.

  фиксирует успех: повторное подтверждение вернёт ссылку без второго POST, а не блокировку.
  Проверено на живой базе, включая потерянный ответ при реально созданном документе.

- **Чистка журнала.** Раз в час удаляются зависшие `.tmp`, «осиротевшие» и завершённые `.lock`,
  а записи с неизвестным исходом — только через год (раньше нельзя, иначе повтор станет
  небезопасным). В README добавлено про том для журнала в Docker.

### Безопасность

- Закрыты все открытые алерты Dependabot (`npm audit` — 0 уязвимостей): `hono`, `@hono/node-server`,
  `fast-uri`, `ip-address`, `qs`, `brace-expansion` (транзитивные, через MCP SDK и eslint);
  обновлены `@modelcontextprotocol/sdk` 1.31, `fast-xml-parser`, `typescript-eslint`, `vitest`.

### Изменено

  без внутренних `$ref` в строках документов, у `operationId` явный UUID-шаблон. Проверено полным
  прогоном 57 инструментов по `tools/list` и живыми сценариями записи.
- **Подтверждение создания без `operationId` отклоняется** — сначала выполните предпросмотр.
- Предпросмотр при выключенной записи (`READ_ONLY=true` или база не `WRITABLE`) не пишет в

## [0.4.0] — 2026-08-21

Запись документов доведена до боевого применения. Основу внёс
**[@Alexsab](https://github.com/Alexsab)** (PR [#19], [#20], [#21]) — он нашёл и
починил то, что не ловится юнит-тестами, только живой базой 1С. Его работа влита
целиком; несколько правок того же класса мы доделали сверху — отмечены как «нашли
при ревью».

### Добавлено

- **`write.document.copy_document` — документ по образцу.** Читает документ целиком
  и пишет копию со ВСЕМИ реквизитами (содержание строк, счета учёта, банковский
  счёт, ответственный, адрес доставки). `create_*` собирают документ из полей своей
  схемы и всё остальное теряют, поэтому ежемесячный документ приходилось дописывать
  руками. Копия непроведённая, номер присваивает 1С; правки — `date`, `fields`
  (шапка), `lines` (строки по номеру). Закрывает и «создать на основании».
- **`content` — реквизит «Содержание»** в строках продажных и закупочных документов.
  Раньше его принимал только счёт поставщика, а в остальных документах поле
  оставалось пустым — 1С его не заполняет сама. Для услуг это блокировало
  выставление: именно «Содержание» печатается в счёте и УПД.
- **Явные счета доходов/расходов** — `incomeAccount` / `expenseAccount` на строку и
  на документ. Значение — код как в 1С (`90.01.2`) или `Ref_Key`; неизвестный код
  даёт понятную ошибку, а не молчаливую подстановку. Приоритет: строка → документ →
  регистр «Счета учёта номенклатуры» → прежние умолчания. Документ, которому нужны
  90.01.2 / 90.02.2, раньше через OData было не создать вовсе.
- **`orgBankAccount`** в счёте покупателю, реализации и акте — название, номер счёта
  или `Ref_Key`. Реквизиты для оплаты печатаются в документе, выбирать их молча нельзя.

### Изменено

- **BREAKING: банковский счёт организации везде зовётся `orgBankAccount`.** Раньше
  один и тот же реквизит назывался в трёх инструментах по-разному — `bankAccount`
  (оплата, списание с р/с) и `orgAccountRef` (платёжное поручение), — и модель,
  выставив счёт, не находила знакомый параметр на оплате. Теперь имя одно, и все
  шесть инструментов принимают название, номер счёта или `Ref_Key` через общий
  резолвер: платёжное поручение раньше понимало только `Ref_Key`. Ломается мало:
  `bankAccount` не работал ни разу с момента появления из-за сломанного фильтра по
  полиморфному `Owner`, так что реально меняется только `orgAccountRef` →
  `orgBankAccount`.

### Исправлено

- **Правка строк документа с табличной частью «Услуги».** `add_document_line`,
  `remove_document_line` и `update_document_lines` читали и патчили только «Товары».
  Акт из `create_act` живёт в «Услугах» — строки уходили в пустую «Товары», сумма
  задваивалась, а удаление строки отвечало «в документе всего 0 строк». Теперь ТЧ
  определяется по факту; поддержан и «Акт об оказании производственных услуг».
- **Банковский счёт организации не подставлялся никогда.** Справочник фильтровался
  по `Owner eq guid'…'`, но `Owner` — полиморфная ссылка, и 1С отвечает на такой
  фильтр 500-й; ошибка гасилась в `catch`. То есть параметр `bankAccount` в
  `create_payment` и `create_bank_writeoff` не работал с самого появления. Теперь
  выборка сужается по `Owner_Type`, владелец сверяется на клиенте, приоритет:
  явный `Ref_Key` → название/номер → основной счёт организации.
- **Правка строк стирала реквизиты прежних строк.** Строка читалась в четыре поля,
  поэтому содержание, счета учёта и номенклатурная группа терялись при каждом
  добавлении или удалении строки. Теперь непересчитываемые поля переносятся как есть.
- **Ошибки ввода отделены от сбоев сервера.** Ненайденный склад, договор или счёт —
  неверные аргументы вызова, но `guard` подписывал им «Внутренняя ошибка
  инструмента». Введён `InputError`: текст отдаётся как есть.
- **Счёт-фактура на акт услуг получал нулевой НДС** *(нашли при ревью)*. Чтение
  документа-основания брало строки только из «Товаров», поэтому
  `create_issued_invoice` и `create_received_invoice` на акте выставляли
  `СуммаНДСДокумента: 0` — ошибка прямо в налоговом документе. НДС собирается по
  обеим табличным частям.
- **Сумма документа со смешанными ТЧ** *(нашли при ревью)*. У реализации бывают
  заполнены и «Товары», и «Услуги»; правка строк и `copy_document` считали итог
  только по правимой части и занижали его на вторую.
- **Сумма НДС строки не теряется при правке** *(нашли при ревью)*. При пересборке ТЧ
  `СуммаНДС` отбрасывалась всегда, и строки документа с НДС уезжали в 1С с нулевым
  налогом. Теперь переносится, если количество, цена, ставка и сумма строки не
  менялись. Пересчёт намеренно не делаем: формула зависит от `СуммаВключаетНДС` и
  процента ставки — угадывать такое нельзя.

- Мажор `typescript` уходит в ignore dependabot рядом с `zod`: TS 7 выходит за

**BREAKING:** все 55 инструментов переименованы с плоского `snake_case`

### Добавлено

  callers can type-check responses». Схемы — в новом `src/schemas/output.ts`;
  большинство write-инструментов сводится к 4 переиспользуемым формам
  (`createResultSchema`/`patchResultSchema`/`mark_for_deletion`/`post_document` —

## [0.1.8] — 2026-06-17

### Исправлено
- **Тихий недосчёт в агрегатах устранён системно.** Аналитика занижала годовые
  итоги на «шумных» базах: выборки стояли под общим `ODATA_MAX_ROWS`=1000, и при
  >1000 документов хвост периода молча отбрасывался (выплаты ИП за год — на ~3 млн
  ₽; затронуты и `get_sales`, `get_cashflow`, `get_debtors`, `get_inventory`).
  Введён единый безопасный путь агрегации (`src/odata/aggregate.ts`): высокий
  потолок `ODATA_ANALYTICS_MAX_ROWS` (200000), и вместо тихой обрезки — **громкая
  ошибка** при переполнении либо **авто-чанкинг по месяцам** (большой период
  досчитывается полностью по окнам). Также: `get_debtors`/`get_inventory` считали
  общий итог только по показанным top-N строкам — теперь по всем.
- Деньги в аналитике суммируются в целых копейках (без float-дрейфа на тысячах
  сумм).

### Добавлено
- Поля `from`/`to`/`asOf` валидируются как дата YYYY-MM-DD (формат + диапазон
  месяца/дня) + проверка `from ≤ to`; раньше кривая дата уходила в OData как есть.
- В ответах аналитики — блок `scan` (`documentsScanned` / `windows` / `elapsedMs`):
  видно, что выборка полная и сколько просканировано.

### Изменено
- Выборки по типам документов в `get_payments_breakdown` / `get_cashflow` идут
  параллельно (быстрее на больших периодах).

### Удалено
- Неиспользуемый `odataDateTime` (латентный UTC-сдвиг даты).

## [0.1.6] — 2026-06-16

### Добавлено
- `get_deal_history` — хронология всех движений по «сделке» (банковский код в
  назначении платежа, напр. CB…) или по договору (contractRef): приход, расход,
  итоги и сальдо. Закрывает вопросы вроде «покажи финрезультат по сделке»,
  «движения по договору №42».
- `get_taxes_paid` — сумма уплаченных налогов/взносов за период с разбивкой по
  статье ДДС (УСН / НДФЛ / страховые / ЕНП / 1% в ПФР), месяцу или получателю.
  Маркер — ВидОперации=«ПеречислениеНалога» (надёжный гейт в БП 3.0). Опц.
  параметр cashflowItem уточняет конкретный вид налога.
- `get_sales_breakdown` и `get_purchases_breakdown` — суммы продаж/закупок за
  период с разбивкой по контрагенту / месяцу / договору / итогу. Фильтры:
  конкретный контрагент, **категория контрагента** (ИП/ЮрЛицо/ФизЛицо/
  Нерезидент/Госорган), договор. Закрывает вопросы «топ покупателей за год»,
  «выручка по месяцам», «сколько закупили у ИП».
- В `get_payments_breakdown` добавлены: `counterpartyKind` (категория), `cashflowItem`
  (статья ДДС по коду/имени/Ref — серверный фильтр), `groupBy:"cashflowItem"`.
  Закрывает вопросы «сколько заплатили ИП за год», «приход/расход по статьям ДДС».
- Параметр `asOf` в `get_debtors` и `get_inventory` — сальдо/остатки на конец
  указанной даты (для аудита, исторических отчётов). Под капотом — параметр
  `Period` виртуальной таблицы `Balance` (path-параметр у регистра, не $filter).

### Добавлено
- `get_payments_breakdown` — высокоуровневая разбивка проведённых
  банковских/кассовых документов за период с фильтрами по направлению
  (приход/расход/оба), контрагенту (Ref_Key), подстроке в назначении платежа,
  виду операции, и разбивкой по виду операции / месяцу / контрагенту / итогу.
  Отвечает на вопросы вроде «сколько процентов по депозиту от <банка> за год»,
  «сколько заплатили такому-то поставщику», «приход по месяцам».
  Контрагент в банковских документах хранится полиморфно — фильтр по нему
  применяется в коннекторе (быстро); назначение/период/орг — на сервере 1С.

### Исправлено
- `search_documents`: фильтр `counterpartyRef` для документов с полиморфным
  полем `Контрагент` (банковские: ПоступлениеНаРасчетныйСчет/СписаниеСРасчетногоСчета
  и т.п.) больше не валит OData ошибкой 400/500: коннектор автодетектит тип поля
  (`Контрагент_Key` → сервер, `Контрагент` → клиент) и фильтрует на своей стороне,
  возвращая пометку `counterpartyFilter`.

## [0.1.5] — 2026-06-16

### Исправлено
- Даты документов уезжали на день назад в часовых поясах с плюсовым смещением:
  `odataDate` форматировал через `toISOString()` (UTC), и локальная полночь
  (напр. 15-е в MSK, +3) превращалась в 21:00 предыдущего дня UTC → 1С писала
  14-е. Теперь берём локальные компоненты даты (Edm.DateTime в 1С — «настенная»
  дата без зоны). Добавлен регресс-тест.

### Добавлено
- `create_supplier_invoice` — регистрация входящего «Счёта на оплату поставщика»
  (основание для оплаты, в т.ч. предоплаты до поставки): без проводок и счетов
  учёта, единая ТЧ «Товары» под товары и услуги (поле `content`/Содержание для
  доставки), реквизиты входящего счёта (`incomingNumber`/`incomingDate`).
- `create_folder` и `move_to_folder` — папки/группы иерархических справочников
  (по умолчанию Контрагенты), вложенность по имени или Ref_Key.
- В `create_nomenclature` — артикул, размещение в папке (`folder`) и признак
  услуги (`isService`).
- В `create_contract` — руководитель/подписант контрагента (`headName`,
  `headPosition`).

### Изменено
- `create_contract`: вид договора (`kind`) теперь обязателен — коннектор не
  угадывает покупатель/поставщик; номер по умолчанию «б/н», дата — сегодня.

## [0.1.0] — 2026-06-16

Первый публичный релиз в npm.

### Добавлено
- **Чтение и аналитика:** список баз/организаций, карта объектов и поля
  (`list_entities` / `describe_entity`), поиск и карточка контрагента, поиск и
  получение документов, дебиторка (сч. 62), остатки (сч. 41/10/43), продажи,
  движение денег, история взаиморасчётов, `health_check`.
- **Мультибаза и мультиорганизация:** параметры `database` и `organization`.
- **Запись (через двойной гейт `READ_ONLY` + `WRITABLE` и dry-run):** создание
  контрагентов, номенклатуры, договоров (вид/валюта/тип цен), счетов покупателю,
  поступлений и реализаций, актов услуг, оплат; проведение/отмена (`post_document`);
  редактирование строк документов; изменение реквизитов (`update_*`); мягкое
  удаление (`mark_for_deletion`).
- Счета учёта документов берутся из регистра «Счета учёта номенклатуры» (откат на
  коды плана счетов); вежливый фоллбэк при отсутствии объекта в «Составе OData».
- npm-пакет с запуском через `npx 1c-odata-mcp`.
