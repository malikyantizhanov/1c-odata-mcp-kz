# Действия в веб-клиенте 1С Fresh: начисление отпускных (исследование и проект)

Статус: **проект, кода нет.** Отмеченное «⚠ проверить» нельзя подтвердить без живой базы 1cfresh.kz.

## Задача

Часть операций 1С через OData не выполнить: суммы по среднему заработку считает модуль формы по кнопке
«Рассчитать». Документ зарплаты, созданный через OData, проводится с нулями и без движений (проверено на живой
базе — `PAYROLL_FORM_HINT` в `src/tools/payroll-sums.ts`). В «Бухгалтерии для Казахстана» отдельного документа
«Отпуск» нет: отпускные — строка `Document_НачислениеЗарплатыРаботникамОрганизаций` с `ВидРасчета` «Отпуск»
(`src/tools/kz-flow.ts`).

Нужен MCP-инструмент «начислить отпускные сотруднику». Он сам нажимает кнопки в веб-клиенте 1С Fresh. Логин и
пароль веб-входа хранятся в базе чата в зашифрованном виде.

## Pomerado: что это

[Pomerado](https://github.com/Pomerado/pomerado): v0.4.0, MIT, Node `>=24.21 <25`, `hostProtocol: 1`.

- **Минтинг.** Агент на моделях OpenAI (нужен `OPENAI_API_KEY`) с настоящим Chromium (Playwright) получает задачу
  на естественном языке. Он сам изучает сайт, пишет TypeScript-модули операции и проверяет их на живом сайте.
  Guardian (тоже модель) проверяет каждое действие и итоговый код. HAR и запись действий не нужны.
- **Результат** — папка с исходниками (`src/`, `pomerado.json` со схемами входа и выхода, `deployment.json`,
  `mcp.mjs`). Каждая интеграция — отдельный MCP stdio-сервер с одним инструментом и `get_job` / `provide_input` /
  `cancel_job`.
- **Выполнение** детерминированное, модель не нужна. Каждый вызов открывает новый контекст браузера без cookies и
  стартует с корня сайта. Если сборка проходила вход, вход повторяется **на каждом вызове**.
- **Логины.** Open-source версия логин не хранит: на каждом запуске спрашивает его через `provide_input` или, в
  режиме библиотеки, через свой колбэк `makeInputAsker`. Сохранённые логины, браузерный парк и автопочинка при
  изменении сайта есть только в платном Pomerado Cloud.
- **Запись.** Минт с `effect: "write"` **один раз выполняет действие по-настоящему** во время сборки.
- **Изоляции нет.** Сгенерированный код выполняется с правами пользователя ОС. Guardian — это ревью моделью, а не
  песочница (так написано в `docs/how-it-works.md` проекта).
- Есть режим библиотеки: `createPomerado`, `makeIntegrationMcp`, точки расширения `pomerado/core/*`. Провайдер
  модели меняется через `ModelProvider` из Agents SDK, но промпты и тесты рассчитаны на OpenAI.

## Подходит ли Pomerado для 1С Fresh

| | Оценка |
|---|---|
| Сайт без API, вход по логину | ✔ это прямой профиль Pomerado |
| Детерминированный прогон без модели | ✔ |
| Веб-клиент 1С | ✖ тяжёлое SPA: кнопки — `div` с `title`, id вида `form3_ФормаРассчитать` (номер формы меняется), модальные окна рисуются внутри страницы, загрузка 20–60 с. Код, который генерирует Pomerado, опирается на доступные имена (accessible name), а у 1С они бедные. Живучесть сгенерированного кода — ⚠ проверить |
| Вход на каждом вызове | ✖ запуск 1С на каждый вызов — плюс 30–60 с и лишний сеанс (лицензии Fresh) |
| Хранить логин у нас | ≈ только в режиме библиотеки: свой `makeInputAsker` отвечает расшифрованным паролем из БД. Тогда нужен свой хост на Node 24 |
| Минтинг записи | ✖ создаёт настоящий документ. Нужна копия базы, а при каждом изменении формы 1С — новый минт |
| Стек | ✖ OpenAI-ключ (у нас MiniMax/GLM), Node 24 (коннектор на Node 22), версия 0.x — интерфейсы хоста ещё меняются |
| Безопасность | ✖ код не изолирован. В `rag-buh` уже есть изолированный `agent-browser`: egress-прокси, allowlist доменов, только публичные IP, `read_only`, `cap_drop: ALL` |

**Вывод.** В прод Pomerado не ставить. Его можно один раз использовать как разведчика на **копии** базы: сделать
минт задачи, прочитать сгенерированные селекторы и шаги и перенести их в свой сценарий. Для прода — свой
детерминированный сценарий на Playwright по гибридной схеме ниже. Он короче и надёжнее того, что сгенерирует
Pomerado: всё, что умеет OData, делаем через OData, а в браузере остаются два нажатия.

Пробный минт (на копии базы, ключ OpenAI — только в окружении):

```sh
npx -y -p pomerado playwright install chromium
claude mcp add pomerado -- npx -y -p pomerado pomerado-mcp mint --root ~/pomerado-integrations
# в чате агента:
# «Pomerado, интеграция onec_vacation_probe, write: войти на https://1cfresh.kz, открыть
#  документ по навигационной ссылке {link}, нажать «Рассчитать», затем «Записать»; вернуть сумму из колонки «Результат»»
```

## Гибридная схема: OData + два нажатия

```
чат (rag-buh) ──X-OneC-Connection (+web-учётка)──► коннектор 1c-odata-mcp-kz
                                                     │ 1. OData: сотрудник, вид расчёта «Отпуск», черновик документа
                                                     │    (Ref_Key = uuidV1 — повтор не создаёт дубль)
                                                     ├──► onec-web-runner (Playwright, отдельный контейнер)
                                                     │    2. вход в 1cfresh → e1cib-ссылка на документ →
                                                     │       «Рассчитать» → «Записать» → выход из сеанса
                                                     │ 3. OData: перечитать «Результат» строки (0 → ошибка)
                                                     ▼
                                       ответ: документ, сумма, «рассчитан, не проведён»
```

### 1. OData: черновик документа

- Сотрудник: `Catalog_СотрудникиОрганизаций` (поиск по ФИО или ref, как в `read.payroll.*`).
- Вид расчёта: план видов расчёта, элемент «Отпуск» (`read.catalog.*` уже читает планы видов расчёта).
- `Document_НачислениеЗарплатыРаботникамОрганизаций`: `Организация_Key`, `ПериодРегистрации` (1-е число
  месяца), строка `Начисления`: `Сотрудник_Key`, `ВидРасчета_Key` и поля периода строки. ⚠ проверить имена
  через `meta.describe_entity`: ожидаются `ДатаНачала` / `ДатаОкончания`.
- `Ref_Key` назначает коннектор (`uuidV1`), запись — по существующему протоколу W: предпросмотр с `operationId`,
  затем `confirm=true`, журнал записи защищает от дублей.

### 2. Браузер: «Рассчитать» и «Записать»

- **Навигационная ссылка** открывает документ сразу, без хождения по меню:
  `https://<хост>/<приложение>/ru_RU/#e1cib/data/Документ.НачислениеЗарплатыРаботникамОрганизаций?ref=<32 hex>`.
  Для GUID `aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee` значение `ref` = `dddd` + `eeeeeeeeeeee` + `cccc` + `bbbb` +
  `aaaaaaaa` (порядок частей у 1С внутренний). ⚠ проверить на живой базе.
- **Селекторы** берём по имени элемента формы, а не по номеру формы: `[id$="_ФормаРассчитать"]`,
  `[id$="_ФормаЗаписать"]`; запасной вариант — `[title="Рассчитать"]`. ⚠ снять точные имена с формы БК КЗ: кнопка
  может быть в командной панели табличной части (`…_НачисленияРассчитать`) или называться «Заполнить и рассчитать».
- **Ожидание.** 1С показывает индикатор длительной операции и блокирует форму. Ждём, пока блокировка снимется и
  в ячейке «Результат» появится число.
- **Вопросы 1С** («Данные были изменены. Сохранить?», «Документ рассчитан неполностью…») — по белому списку
  ожидаемых текстов. Любое другое окно — сбой с текстом окна и скриншотом. Пароль на скриншот не попадает: шаг входа
  не снимается.
- **Сеанс.** В конце — «Выход» из 1С, чтобы освободить лицензию Fresh. На одну базу — не больше одного сеанса
  (очередь в исполнителе).
- **Вход в 1cfresh.** Форма портала, затем запуск приложения. ⚠ проверить: адрес формы, есть ли 2FA или капча,
  совпадает ли веб-учётка с учёткой OData. Обычно не совпадает: OData ходит пользователем приложения с правом
  «Стандартный интерфейс OData», а веб — пользователем портала.

### 3. OData: проверка результата

Перечитать документ. В строке «Отпуск» `Результат > 0` — успех, иначе ошибка «1С не рассчитала отпускные» со
скриншотом формы. **Не проводить.** Проведение — отдельный существующий опасный инструмент
`write.document.post_document`, то есть второе нажатие в чате.

## Инструмент MCP

`write.payroll.vacation_accrual`, протокол W (как остальные пишущие):

```jsonc
// вход
{ "database": "…", "organization": "…?", "employee": "ФИО | ref",
  "dateFrom": "2026-11-02", "dateTo": "2026-11-25", "registrationPeriod": "2026-11?",
  "confirm": false, "operationId": "…" }
// предпросмотр: сотрудник, вид расчёта, период, дней, план «создать черновик → Рассчитать → Записать»
// запись (confirm=true):
{ "status": "calculated_not_posted", "documentRef": "…", "number": "…", "amount": 412345.67,
  "write_status": "done | ui_failed | unknown", "screenshot?": "resource" }
```

- `write_status: "ui_failed"`: черновик создан, но не рассчитан. Повтор с тем же `operationId` не создаёт новый
  документ, а повторяет шаг 2 на этом черновике.
- Публикация: `ODATA_HTTP_WRITE_TOOLS` у коннектора, `ONEC_WRITE_TOOLS` и `ToolUX` (вид `create`) в
  `rag-buh/backend/app/services/onec_tools/families/`. Тогда форма в чате появится сама.

## Где выполнять браузер

**Рекомендация:** отдельный контейнер `onec-web-runner` (Node + Playwright, по образцу `rag-buh/agent-browser`:
`read_only`, `cap_drop: ALL`, egress только на `*.1cfresh.kz`, порт наружу закрыт). Коннектор вызывает его по
внутренней сети `onec` с токеном. Chromium в образ коннектора не добавляем: он держит OData-учётки, и размер
образа и поверхность атаки должны оставаться минимальными.

Альтернатива — сценарный эндпоинт в существующем `agent-browser` (Python), уже изолированном. Минус: тогда
браузер вызывает бэкенд, а не MCP, и маршрут перестаёт быть целиком «в MCP».

## Учётные данные

Существующая схема почти всё покрывает:

- `rag-buh`: в `onec_connections` добавить `web_username` и `web_password_enc` (Fernet через
  `services/secrets.py`, ключи `ONEC_SECRET_KEYS`, ротация — как у пароля OData), плюс миграция. В окне «Подключения
  1С» — необязательный блок «Вход в веб-клиент (для расчётов в браузере)» и кнопка «Проверить вход».
- В ответах API пароля нет. Бэкенд расшифровывает пароль на время запроса и кладёт его в `X-OneC-Connection` как
  необязательный `web: {username, password}` (в `HeaderSchema` в `src/http/pool.ts`).
- Коннектор и исполнитель ничего не хранят. Ключ пула — хеш учётки, его уже считает `pool.ts`. В логах учёток нет.
- Без веб-учётки инструмент сразу отвечает «Для расчёта отпускных добавьте вход в веб-клиент в подключении».

## План работ

1. **Разведка (½–1 день, нужна копия базы).** Метаданные строки `Начисления`, имена кнопок формы, формат
   e1cib-ссылки, вход в 1cfresh (2FA? совпадение учёток?). По желанию — пробный минт Pomerado для сравнения.
2. **Исполнитель (2–3 дня).** Контейнер `onec-web-runner`: вход, открыть по ссылке, нажать по белому списку
   действий, выход; очередь по базе; скриншоты при сбое. Тесты — на локальной HTML-странице, похожей на форму 1С.
3. **Инструмент коннектора (1–2 дня).** `write.payroll.vacation_accrual` (W-протокол, журнал, повтор шага 2),
   контрактные тесты, `docs/HTTP-MODE.md`.
4. **rag-buh (1–2 дня).** Поля веб-учётки, миграция, форма подключения, `ToolUX`, белые списки, тесты.
5. **Живой прогон** на копии базы, затем бета через `ONEC_BETA_EMAILS`.

Тот же исполнитель потом подойдёт для других «форменных» действий: «Заполнить» в документах зарплаты, закрытие
месяца, больничные.
